## Financial corrections and original causes

1. **Duplicate allocation definitions:** earlier views compared income shares with spending targets, mapped unknown cash/fees into different tiers and could exceed a 100-point score. All callers now use `expense_allocation.py`. Shares are category amount / total spending. Unknown amounts remain separate; no score is given when classification is incomplete or component totals are inconsistent. The complete-data score is `100 * total variation distance = 50 * sum(abs(actual_share - target_share))`, mathematically bounded 0-100. Source history uses the trailing 12 recorded months; standing orders are not added again.
2. **Colour policy:** each tier uses its own target: Base 50%, Middle 30%, Peak 20%. Over target is red; at target or up to five percentage points below is yellow; farther below is green. Colour describes allocation, not affordability. Backend and shared frontend helpers have threshold tests.
3. **Peak reduction:** reducing spending also reduces the denominator. To reach 20% by removing Peak expense, `cut = max(0, (Peak - .20 * total) / .80)`. This is explicitly a hypothetical reduction requiring purchase verification. A balanced-looking allocation cannot erase a cash-flow deficit.
4. **Rounding and cash flow:** income/spending medians are rounded to monetary cents before subtraction. Directory net cash flow is recomputed using the same convention instead of showing a conflicting processed-snapshot tie rounding. Source CSV/database records are unchanged.
5. **Forecast indexing/dates:** projections start at the actual recorded month-end balance, not a made-up 28th or an incorrectly advanced reference day. Regression coordinates reflect calendar gaps. Monthly spending is nonnegative. Daily calendar income/outflow allocation generates both chart and table dates/values. Source income uses the recorded median. Shock changes end after the selected duration; one-off cost is deducted once. Benchmark runway remains separately labelled as constant-cost buffer/gap, capped at 120 months. A missing daily runway means no depletion within the 365-day horizon, not infinite guaranteed safety.
6. **Optimization and backup:** 10%, 20% and contingency 30% Peak cuts rerun the same forecast. Baseline/improved 90-day balances and finite runway differences are returned. Fixed 45/60/90-day gains, minimum 1.5-month gains and synthetic subscription-saving additions were removed.
7. **Goals:** target is four times typical monthly spending. Remaining target accounts for the recorded closing balance, including a negative balance. Aspiration is 12% of income with a 100-unit floor only when income and a reserve gap exist. Affordable contribution is capped by positive net cash flow and the remaining gap. Required budget improvement is explicit; zero affordable contributions produce no invented completion date. Completion uses ceiling division; every-two-week contribution is monthly * 12 / 26.
8. **Lending:** payments use Decimal arithmetic and a reconciled final installment. Total repayment equals principal + financed fee + total interest. Illustrative APR is 12 times the monthly IRR of actual cent-rounded payments against net principal. This distinguishes financed fees from a nominal interest rate; it is not a regulated lender quote. Revolving examples show modeled rather than approved limits and any uncovered shortfall. No arbitrary 1,500-unit emergency is inserted when costs are zero.
9. **Subscriptions/inflation/fraud uncertainty:** no invented subscriptions, service identities, due dates, duplicate-service savings, CPI values or empty-history statistical baselines. Recorded recurring patterns and unknowns remain identifiable. Fraud outputs request hypothetical review rather than transaction approval.

## Exact startup instructions

In PowerShell, stop an older development server with Ctrl+C, then:

```powershell
Set-Location 'C:\Users\chaud\OneDrive\Desktop\Sheridan\draft 4\financial-resilience-engine'
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

Open `http://127.0.0.1:8000/`, hard-refresh with Ctrl+F5, sign in using the existing administrator account, then search `20111` or another imported ID in Account Analysis and choose View account analysis. Imported data remains read-only. Ordinary client sign-in opens its personal workspace; admin personal tools are collapsed and separate.

For a fresh installation only, create a venv, run `python -m pip install -e ".[dev]"`, configure `.env`, apply `python -m scripts.migrate`, and provision an administrator with `python -m scripts.create_admin --email admin@tangerine.com`. Do not overwrite an existing `.env` or reimport the populated database just to start the app.
